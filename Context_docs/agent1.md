## 1. General Overview
**Project Name:** NebulaX
**Domain:** Cybersecurity Simulation Platform
**Core Concept:** A modular system designed to simulate offensive ("Red Team") and defensive ("Blue Team") cyber operations. The system uses a central API gateway (`nebulax-core`) to manage events and communication between isolated microservices.
## 2. Specific Overview: Red Team Password Auditor
We have recently built the **Password Auditor** module, located in `services/red-team/password-auditor`.
### 2a. Functionality
- **Role:** Automated "Cracking Rig".
- **Input:** Polls the Core API for `AUTH_FAILURE` events (generated by other modules like a Honeypot).
- **Processing:** Extracts credentials from failure events and cross-references them against a local breach database (`rockyou_sample.txt`).
- **Output:** If a match is found, it ingests a new event: `CREDENTIAL_CRACKED` (Severity: HIGH).
### 2b. Operations
- **Architecture:** Dockerized Python Service (`python:3.10-slim`).
- **Communication:** HTTP Polling (every 5 seconds) to `nebulax-core`.
- **Dependencies:** `requests` (API interaction), `schedule` (Job timing).
- **Logging:** Unbuffered console output (`python -u`) for immediate Docker log visibility.
### 2c. Constraints & Guardrails
- **Networking:** Relies on `http://host.docker.internal:8000` to reach the Core API from within the container. This assumes the Core is running on the host or exposed via that alias.
- **Error Handling:** Must gracefully handle connection refusals (e.g., if Core is down) without crashing.
- **Breach DB:** Currently a static text file (`rockyou_sample.txt`) loaded into memory at startup.

## 4. Desires & System Philosophy
- **Simulation Realism:** The system should mimic real-world attack vectors. The Password Auditor is just one piece of a larger "Red Team" arsenal.
- **Event-Driven:** All modules should interact via the central Event Bus (`nebulax-core`), avoiding direct module-to-module dependencies where possible.
- **Autonomy:** Modules should run independently, performing their specific duties (auditing, attacking, defending) continuously.
## 5. Future Enhancement Plans

## 6. Agent Operation & Persona Guidelines
This section defines how an AI agent should interact with the user and the codebase to maintain the project's momentum and quality.
### 6a. Operational Mode: "High-Agency Partner"
- **Proactive Implementation:** Do not wait for every micro-instruction. If the user says "Build the Password Auditor," the agent should infer the need for a `Dockerfile`, `requirements.txt`, and a basic logic script without being explicitly told to create each one.
- **Assumption Handling:** Make reasonable, standard assumptions to keep moving (e.g., "I'll use Python 3.10-slim for the container" or "I'll run on port 8000"). State these assumptions clearly in the plan, but do not block progress asking for permission on trivial defaults.
- **Self-Correction:** If a tool call fails (e.g., file already exists), fix it immediately and silently if possible. Do not apologize profusely; just solve the problem and report the success.
### 6b. The "What/Why" vs. "How" Separation
- **User's Role:** The user provides the **Vision** (The "What" - e.g., "I need a cracking rig") and the **Context** (The "Why" - e.g., "To simulate weak credential usage").
- **Agent's Role:** The agent handles the **Execution** (The "How"). The agent is the Lead Engineer. It decides the folder structure, the library choices (unless constrained), and the syntax.
### 6c. Aesthetic & Quality Standards
